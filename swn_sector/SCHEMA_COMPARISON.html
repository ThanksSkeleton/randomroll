SWN sector data schema comparison

A field-by-field comparison of the full generator's SectorV4 output and the prototype UI's Sector domain model, revised around a single merged domain that retains the useful information from both projects.

Executive summary

Merge the two contracts into one canonical domain model.

Both models describe sectors, systems, stars, worlds, and points of interest, but they optimize for different jobs. The generator is a strict, deeply nested content model. The prototype is a flatter application model built for selection, visibility, editing, routes, and ship movement. The target is the cross-product of their useful information: generator richness plus UI/application state, with either project changed as necessary.

Merge one model
Retain both sides

Keep rich generator facts alongside UI names, visibility, routes, selection identity, editing, and ship state.

Restructure freely

Nesting, casing, and side tables are implementation choices; no current structure is presumed canonical.

Retire low-value mechanics

Remove habitable-slot and orbital-position-category data rather than carrying it into the merged model.

Known minor fix: grid orientation

The intended grid is 10 columns × 8 rows. The generator's current 8 × 10 contract is accidentally transposed and will be corrected later. This is a bounded coordinate fix, not a structural merge concern.

Structural priority: no lossy UI projection

Tags, attributes, planet details, habitability, object kinds, routes, visibility, and campaign state should all receive first-class homes in the merged schema. Generic display strings must not become the only copy of structured data.

Warp model decision

Remove the IngressEgress region and its ingress/egress POIs. A system's warp boundary is derived by multiplying the outermost direct-orbit object’s AU by a universal boundary multiplier. Every route portal stores a fixed angle on its connected system's boundary.

Proposed canonical schema · sector, UI state, and routes

Concrete TypeScript-style proposal. Every property below has one defined meaning; generated facts and UI disclosure text remain separate.

  Id: Guid;

interface Sector {
  SchemaVersion: "merged-v1";
  OriginalSeed: string; // provenance; not a complete replay specification
  SectorName: string;
  Systems: StarSystem[];
  Routes: Route[];
  RoutePortals: RoutePortal[];

interface Route extends SelectableEntity {
  PortalIds: [Guid, Guid];
}

interface RoutePortal extends SelectableEntity {
  RouteId: Guid;
  SystemId: Guid;
  BoundaryAngleDegrees: number; // 0 inclusive, 360 exclusive
}

interface PlayerShip extends SelectableEntity {
  CurrentLocationId: Guid; // system-contained location, route portal, or route
}

Every route references exactly two distinct portals. Each portal exists, references that same route, belongs to a different existing system, and belongs to no other route. Portal angles are valid boundary angles. A ship location must resolve to an allowed location and may not refer to the ship itself.

Detailed temperature and AU placement

Temperature is the one authoritative thermal value. Temperature rank and the temperature contribution to habitability are derived from it; neither is generated, serialized, nor independently edited. Higher rank means hotter.

For direct-orbit system objects, star type and detailed temperature constrain a randomized AU placement roll: hotter objects around the same star must be closer, colder objects farther, and equal-temperature objects must receive distinct non-colliding distances. The selected AU remains generated and serialized data. Asteroid belts require Volcanic through Alpine temperatures; Kuiper belts and gas clouds require Boreal through Cryogenic temperatures; independent stations may have any temperature. Moons have their parent planet's temperature and star-relative AU; their retained angle is presentational and no moon-to-planet distance is modeled.

Special cases removed or altered

  • Max Environment Hab is removed. Environmental complications such as poison storms or radioactive dust are applied ad hoc in narrative rather than as generator constraints.
  • Flying Cities no longer creates or requires the NONTERRESTRIAL state.
  • Primitive Aliens and Xenophiles are removed because they require generating a sapient alien race.
  • The world-tag table is reduced to 98 entries and must be reindexed to a contiguous 1–98 range; removing the current entries alone would otherwise leave gaps at rolls 64 and 98.
  • Planet archetypes become generator-only templates. For example, Venusian, Jovian, and Neptunian templates are expanded and varied into complete uninhabited Planet records before serialization; the canonical model and UI receive the resulting physical facts, not an archetype marker or a lesser planet shape.
  • Jovian and Neptunian planets use Size: "Jupiter" or Size: "Neptune" with the matching "Jovian Gas" or "Neptunian Gas" bulk composition. Their remaining planet fields are populated by the template, including InhabitedInfo: false and SurfaceWaterPresent: false.

Points of interest

Keep id and point, then add the UI's explicit ParentObjectId and display/detail/visibility state. Occupant and situation narrative is covered by IntelligenceText; generation rolls are bookkeeping and are not retained.

The current generator's kind discriminator only distinguishes ingress, egress, and other. Once warp-point POIs are removed, it carries no useful information; point becomes the canonical POIType.

Parent/child representation

A Planet can orbit any other system object. Orbit.ParentObjectId supports that relationship without restricting it to the prototype's narrow World → World relationship.

Parent/child relationships are derived from this reference rather than duplicated as serialized satellite lists. The gas-giant-moon generation roll is bookkeeping and is not retained.

Replacement warp-boundary rule

directOrbitObjects = system.Objects.filter(object =>
  object.Orbit.ParentObjectId === null
);

outermostObjectAU = max(directOrbitObjects.map(object => object.Orbit.AU));

systemBoundaryAU =
  outermostObjectAU * UNIVERSAL_SYSTEM_BOUNDARY_MULTIPLIER;

routeMarkerPosition = polarPoint(
  systemBoundaryAU,
  routePortal.BoundaryAngleDegrees
);

Only direct-orbit objects set the boundary; child objects do not. Each route owns two top-level portals, one at each connected system; their fixed angles can differ.

UI information to add to the canonical model

Details and visibility

The UI stores names and tiered text in a side table keyed by selectable object ID:

  • ProceduralName and editable NiceName
  • VisibilityLevel: none, basic scan, partial culture, or full culture
  • Summary, scan, culture, and GM-only text blocks

Retain all of this. Generated structured facts remain separate; the tiered strings describe what the UI reveals rather than replacing the underlying data.

Routes and player ship

A Route links two top-level RoutePortal entities, each on a different system boundary. A portal is selectable but not a point of interest. PlayerShip.CurrentLocationId may name a system-contained location, a portal, or a route; only a route location has no current system. Retain this mutable campaign state separately from procedural facts.

Route creation, portal creation and angle assignment, and initial ship placement become explicit generation/initialization responsibilities.

Exact-one detail invariant

The UI validator requires the IDs in DetailsAndVisibility to match the complete selectable-ID set exactly. In the merged model, extend that concept to every first-class system object—not just worlds—plus systems, stars, POIs, routes, route portals, and the player ship. Whether the detail state stays in a side table or moves onto each entity is a structural choice.

Suggested implementation sequence

  1. Design the canonical entity model. Start with a first-class Planet/OtherCelestialObject discriminated union.
  2. Mark intentional deletions. Remove orbital-position category, habitable slot, maximum habitable slots, empty slots, ingress/egress regions, warp-point POIs, and dependent rules.
  3. Move the generator onto the new model. Expand internal planet archetype templates into complete planet records, then generate final IDs, object relationships, structured non-planet object types, display angles, names/details defaults, and route inputs directly.
  4. Move the UI onto the new model. Render every system-object kind and update selection, containment, editing, deletion, visibility, and ship movement.
  5. Unify schema and validation. Cover generation rules and graph integrity in one contract/test suite; then remove both obsolete models.

Structural recommendations

  • Use a discriminated union for Planet and OtherCelestialObject. Jovian and Neptunian bodies are planets; structured ObjectType values distinguish the remaining non-planets such as belts, clouds, and stations.
  • Use a general parent-object relationship so satellites and POIs can reference any permitted object kind.
  • Represent warp travel through routes and first-class route portals: every route names exactly two portals, and every portal names its route, system, and fixed boundary angle.
  • Keep generator facts structured; display/intelligence text augments rather than replaces them.
  • Treat the persisted Sector as a mutable snapshot: generated facts and campaign state share the snapshot, while OriginalSeed records provenance rather than promising deterministic reconstruction.
  • Add an explicit schema version and, if sectors need stable archive identity, a sector ID distinct from seed.
  • Generate stable IDs at object creation time so generation and UI share identity without a conversion phase.
  • Fix the 10 × 8 coordinate bounds independently; it need not block structural design.
Information retention checklist
  • Sector: schema version, seed, name, systems, routes, and archive identity if needed.
  • System/star: IDs, 10 × 8 hex, star type, habitability rating, names/details, and visibility.
  • Planets: terrestrial, Jovian, and Neptunian physical facts, atmospheric data, identity, orbit/parent, and UI state; inhabited-only data lives in InhabitedInfo.
  • Other celestial objects: identity, structured object type, orbit/parent, POIs, and UI state.
  • POIs: ID, POI type, a system-object parent, names/details, and visibility.
  • Campaign/UI: route portals with route/system references and angles, ship location, procedural/editable names, summary and intelligence tiers, visibility, and selectable identity.

Intentionally not retained: orbitalPositionCategory, habitableSlot, maxHabitableSlots, empty slot records, IngressEgress locations, and ingress/egress POIs. A slot ID is unnecessary if it identifies only a removed wrapper.
