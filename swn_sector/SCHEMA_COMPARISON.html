SWN sector data schema comparison

A field-by-field comparison of the full generator's SectorV4 output and the prototype UI's Sector domain model, revised around a single merged domain that retains the useful information from both projects.

Executive summary

Merge the two contracts into one canonical domain model.

Both models describe sectors, systems, stars, worlds, and points of interest, but they optimize for different jobs. The generator is a strict, deeply nested content model. The prototype is a flatter application model built for selection, visibility, editing, routes, and ship movement. The target is the cross-product of their useful information: generator richness plus UI/application state, with either project changed as necessary.

Merge one model
Retain both sides

Keep rich generator facts alongside UI names, visibility, routes, selection identity, editing, and ship state.

Restructure freely

Nesting, casing, and side tables are implementation choices; no current structure is presumed canonical.

Retire low-value mechanics

Remove habitable-slot and orbital-position-category data rather than carrying it into the merged model.

Known minor fix: grid orientation

The intended grid is 10 columns × 8 rows. The generator's current 8 × 10 contract is accidentally transposed and will be corrected later. This is a bounded coordinate fix, not a structural merge concern.

Structural priority: no lossy UI projection

Tags, attributes, planet details, habitability, civilization tier, rolls, object kinds, routes, visibility, descriptions, and campaign state should all receive first-class homes in the merged schema. Generic display strings must not become the only copy of structured data.

Warp model decision

Remove the IngressEgress region and its ingress/egress POIs. A system's warp boundary is derived by multiplying the outermost direct-orbit planet's AU by a configured boundary multiplier. Every route endpoint stores a fixed angle on its connected system's boundary.

Legend: retain merge/restructure new field needed structure choice retire

Points of interest

Keep id, point, roll, occupant, and situation, then add the UI's explicit ParentObjectId and display/detail/visibility state.

The current generator's kind discriminator only distinguishes ingress, egress, and other. Once warp-point POIs are removed, it carries no useful information; point becomes the canonical POIType.

Parent/child representation

A generated PrimaryPlanet can orbit a gas giant. Orbit.ParentObjectId supports that relationship without restricting it to the prototype's narrow World → World relationship.

isGasGiantMoon and a gas giant's satellite list are derived from this relationship rather than serialized as duplicate facts. The original gasGiantMoonRoll remains in PlanetDetails.

Replacement warp-boundary rule

directOrbitPlanets = system.Objects.filter(object =>
  object.Orbit.ParentObjectId === null &&
  (object.Kind === "PrimaryPlanet" ||
   object.Kind === "SecondaryPlanet" ||
   object.Kind === "GasGiant")
);

outermostPlanetAU = max(directOrbitPlanets.map(object => object.Orbit.AU));

systemBoundaryAU =
  outermostPlanetAU * sector.TravelRules.SystemBoundaryMultiplier;

routeMarkerPosition = polarPoint(
  systemBoundaryAU,
  routeEndpoint.BoundaryAngleDegrees
);

Other objects, stations, and satellites do not set the boundary. A route stores one endpoint angle for each connected system, so the same route can meet the two system boundaries at different fixed angles.

UI information to add to the canonical model

Details and visibility

The UI stores names and tiered text in a side table keyed by selectable object ID:

  • ProceduralName and editable NiceName
  • VisibilityLevel: none, basic scan, partial culture, or full culture
  • Summary, scan, culture, and GM-only text blocks

Retain all of this. Generated structured facts remain separate; the tiered strings describe what the UI reveals rather than replacing the underlying data.

Routes and player ship

Route links two systems. PlayerShip points to a current system and selectable location. Retain both in the combined project, while distinguishing generated sector facts from mutable campaign state.

Each route endpoint gains a fixed boundary angle. Route creation, endpoint-angle assignment, and initial ship placement become explicit generation/initialization responsibilities.

Exact-one detail invariant

The UI validator requires the IDs in DetailsAndVisibility to match the complete selectable-ID set exactly. In the merged model, extend that concept to every first-class system object—not just worlds—plus systems, stars, POIs, routes, and the player ship. Whether the detail state stays in a side table or moves onto each entity is a structural choice.

Suggested implementation sequence

  1. Design the canonical entity model. Start with the information cross-product and a first-class discriminated system-object union.
  2. Mark intentional deletions. Remove orbital-position category, habitable slot, maximum habitable slots, empty slots, ingress/egress regions, warp-point POIs, and dependent rules.
  3. Move the generator onto the new model. Generate final IDs, object relationships, display angles, names/details defaults, and route inputs directly.
  4. Move the UI onto the new model. Render every system-object kind and update selection, containment, editing, deletion, visibility, and ship movement.
  5. Unify schema and validation. Cover generation rules and graph integrity in one contract/test suite; then remove both obsolete models.

Structural recommendations

  • Use a discriminated union for planets, gas giants, other objects, and independent stations.
  • Use a general parent-object relationship so satellites and POIs can reference any permitted object kind.
  • Represent warp travel entirely through routes: each endpoint names a system and a fixed boundary angle.
  • Keep generator facts structured; display/intelligence text augments rather than replaces them.
  • Separate generated sector content from mutable campaign state such as visibility and ship location.
  • Add an explicit schema version and, if sectors need stable archive identity, a sector ID distinct from seed.
  • Generate stable IDs at object creation time so generation and UI share identity without a conversion phase.
  • Fix the 10 × 8 coordinate bounds independently; it need not block structural design.
Information retention checklist
  • Sector: schema version, seed, name, systems, routes, and archive identity if needed.
  • System/star: IDs, 10 × 8 hex, star type, roll, habitability rating, names/details, and visibility.
  • Primary worlds: every tag, attribute, planet-detail field, state, habitability result, civilization tier, identity, orbit/parent, and UI state.
  • Other system objects: exact kind, archetype, category, description, satellites/parent, POIs, AU, angle, and UI state.
  • POIs: ID, POI type, roll, occupant, situation, parent object, names/details, and visibility.
  • Campaign/UI: route endpoint systems and angles, boundary multiplier, ship location, procedural/editable names, summary and intelligence tiers, visibility, and selectable identity.

Intentionally not retained: orbitalPositionCategory, habitableSlot, maxHabitableSlots, empty slot records, IngressEgress locations, and ingress/egress POIs. A slot ID is unnecessary if it identifies only a removed wrapper.
